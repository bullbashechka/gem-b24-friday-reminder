# b24-friday-reminder

Бот-напоминалка для Битрикс24: каждую пятницу пишет сотрудникам с задачами на сегодня чек-лист дел перед концом недели. Весь проект живёт на VPS.

## Стек

- Node.js 20 LTS
- Зависимости: `axios`, `dotenv`, `pino`
- Cron — системный
- Git для версионирования
- Логи в файл, ротация через `logrotate`

## Важное про вебхук

Свой входящий endpoint не делаем: Битрикс не должен вызывать наш сервер по событию.

Нужен только входящий вебхук Битрикс24 как простой REST-ключ. Скрипт сам раз в час просыпается по cron, получает актуальный список задач и отправляет сообщения через REST.

## Как создать входящий вебхук в Битрикс24

1. Войти в Битрикс24 под тех.юзером, от имени которого должны уходить сообщения. Лучше отдельный пользователь «Контроль пятницы», а не личный аккаунт.
2. Открыть `Приложения` → `Разработчикам` → `Другое` → `Входящий вебхук`.
3. Название: `Friday reminder`.
4. Права доступа:
   - `task` — читать задачи через `tasks.task.list`
   - `im` — отправлять личные сообщения через `im.message.add`
   - `user` — не нужен для базовой версии; добавить только если потом понадобится искать пользователей через `user.get` / `user.search`
5. Сохранить вебхук и скопировать URL вида:

```
https://portal.bitrix24.ru/rest/USER_ID/WEBHOOK_CODE/
```

6. В `.env` вставить URL целиком:

```
WEBHOOK_URL=https://portal.bitrix24.ru/rest/USER_ID/WEBHOOK_CODE/
```

Важно: этот URL является секретом. Его нельзя коммитить, отправлять в чатах и хранить в README.

## REST-методы, которые используем

### 1. Проверка вебхука

Метод:

```
profile
```

Пример:

```bash
curl -X POST "$WEBHOOK_URL/profile.json"
```

Нужен один раз при настройке. Если вебхук живой, Битрикс вернёт данные пользователя, под которым создан вебхук.

### 2. Получить задачи с дедлайном сегодня

Метод:

```
tasks.task.list
```

Endpoint:

```
POST ${WEBHOOK_URL}tasks.task.list.json
```

Тело запроса:

```json
{
  "order": {
    "DEADLINE": "asc"
  },
  "filter": {
    ">=DEADLINE": "2026-06-12T00:00:00+05:00",
    "<=DEADLINE": "2026-06-12T23:59:59+05:00"
  },
  "select": [
    "ID",
    "TITLE",
    "STATUS",
    "REAL_STATUS",
    "DEADLINE",
    "RESPONSIBLE_ID"
  ],
  "start": 0
}
```

В коде даты подставляются динамически по `TIMEZONE`. После получения задач фильтруем в JS только незакрытые статусы:

```
2 — ждёт выполнения
3 — выполняется
4 — ждёт контроля
```

Закрытые/неактуальные не трогаем:

```
5 — завершена
6 — отложена
7 — отклонена, если такой статус придёт в ответе
```

Пагинация обязательна: Битрикс отдаёт список страницами. Запускаем запрос с `start = 0`, потом повторяем со следующим `start`, пока страницы не закончатся.

### 3. Отправить личное сообщение сотруднику

Метод:

```
im.message.add
```

Endpoint:

```
POST ${WEBHOOK_URL}im.message.add.json
```

Тело запроса:

```json
{
  "DIALOG_ID": "123",
  "MESSAGE": "Привет! Пятница, перед концом дня нужно:\n\n☐ Сдвинуть задачи с дедлайном на сегодня + комментарий по каждой\n☐ Закрыть открытые обращения в Коннекте\n☐ К обращениям «в работе» — привязать задачу\n\nНапомню через час, если задачи на сегодня ещё останутся.",
  "SYSTEM": "N",
  "URL_PREVIEW": "N"
}
```

`DIALOG_ID` для личного чата — это ID пользователя из `RESPONSIBLE_ID`.

### 4. Тестовая отправка себе

На этапе настройки нужно взять свой Bitrix user ID и выполнить:

```bash
curl -X POST \
  -H "Content-Type: application/json" \
  -d "{\"DIALOG_ID\":\"YOUR_USER_ID\",\"MESSAGE\":\"Тест Friday reminder\",\"SYSTEM\":\"N\",\"URL_PREVIEW\":\"N\"}" \
  "$WEBHOOK_URL/im.message.add.json"
```

Если сообщение пришло, право `im` настроено правильно.

## Логика скрипта

Один запуск = один прогон, без состояния между запусками:

1. Текущая дата в TZ портала, границы 00:00–23:59
2. `tasks.task.list` с пагинацией: дедлайн в этих границах, статус не закрыт, `select` только `RESPONSIBLE_ID`
3. Дедуплицировать исполнителей
4. Каждому отправить `im.message.add` с `DIALOG_ID = uid`
5. Залогировать: кому отправили, сколько задач у каждого, ошибки
6. Выход

Цикл повторений делает системный cron, а не скрипт.

## Cron на VPS

```
0 9-18 * * 5  cd /opt/b24-friday-reminder && /usr/bin/node src/index.js >> logs/app.log 2>&1
```

## Этапы работ

### Этап 1. Подготовка в Битриксе *(15 минут)*

- Создать тех.юзера «Контроль пятницы»
- Войти под ним → Разработчикам → Другое → Входящий вебхук
- Права: `im`, `task`
- Сохранить URL вебхука

### Этап 2. Подготовка VPS *(20 минут)*

- Установить Node.js 20 LTS (через nvm или nodesource)
- Создать пользователя проекта или работать под существующим
- `mkdir -p /opt/b24-friday-reminder && cd /opt/b24-friday-reminder`
- `git init` или сразу `git clone`, если репо уже на GitHub/Gitea

### Этап 3. Каркас проекта *(30 минут)*

- `npm init -y`
- `npm i axios dotenv pino`
- Создать структуру файлов
- `.gitignore` для `node_modules`, `.env`, `logs/`
- `.env.example` с пустыми значениями
- `README.md` с кратким описанием

### Этап 4. REST-обёртка `bitrix.js` *(30 минут)*

- Функция `call(method, params)` — POST на `${WEBHOOK_URL}${method}.json`
- Обработка ошибок Битрикса (поле `error` в ответе)
- Логирование вызовов

### Этап 5. Сбор исполнителей `tasks.js` *(40 минут)*

- Функция `getTodayDeadlineUsers()`
- Пагинация: Битрикс отдаёт по 50, нужен цикл по `start`
- Корректные границы даты с учётом TZ портала
- Дедупликация и возврат массива uid
- Тест-запуск: вывести список в консоль

### Этап 6. Отправка сообщений `messages.js` *(20 минут)*

- Константа с текстом чек-листа
- Функция `sendReminder(userId)` — вызов `im.message.add` с `DIALOG_ID = userId`
- Тест-запуск: отправить себе

### Этап 7. Сборка `index.js` *(20 минут)*

- Загрузка env, инициализация логгера
- Получить список uid → пройтись циклом → отправить каждому
- Финальный лог: общая статистика прогона
- Корректный exit code (0 — ок, 1 — фатальная ошибка)

### Этап 8. Боевая проверка вручную *(30 минут)*

- Создать тестовую задачу с дедлайном сегодня на себя или коллегу
- Запустить `node src/index.js`
- Проверить, что сообщение пришло
- Проверить логи

### Этап 9. Cron *(15 минут)*

- `crontab -e`, добавить одну строку расписания
- **Важно:** указать полный путь к `node` (`which node` → подставить результат)
- Поставить временно на ближайшую минуту для теста, убедиться что запускается

### Этап 10. Логирование и ротация *(15 минут)*

Создать `/etc/logrotate.d/b24-friday-reminder`:

```
/opt/b24-friday-reminder/logs/app.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
}
```

Проверка: `logrotate -d /etc/logrotate.d/b24-friday-reminder`

### Этап 11. Первая боевая пятница

- В 9:05 заглянуть в логи
- В 10:05 проверить второй запуск
- Если что-то не так — поправить, передеплоить, дождаться следующего часа

### Этап 12. Документация в README

- Как развернуть с нуля
- Как менять текст сообщения
- Как смотреть логи (`tail -f logs/app.log`)
- Как временно отключить (закомментировать строки в crontab)

## Что нужно держать в голове

- `node` в cron-окружении не имеет того же PATH, что в shell. Всегда полный путь: `/usr/bin/node` или `/root/.nvm/versions/node/v20.x.x/bin/node`
- TZ на VPS: проверить `timedatectl` — если сервер в UTC, а портал в Алматы, корректировать в коде, а не полагаться на системную зону
- Битрикс лимит ~2 req/sec, при 50+ исполнителях между отправками `await sleep(500)`
- В первый раз тестировать на одном-двух людях, а не сразу на всём отделе
